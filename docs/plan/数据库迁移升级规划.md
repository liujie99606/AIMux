# 数据库迁移升级规划

## 1. 目标与兼容边界

AIMux 从引入 Alembic 的版本开始正式管理数据库版本。引入时的当前完整数据库结构定义为第一个基线 revision：`001_current_baseline`。此前 Git 历史中的建表、补列、密钥加解密等变化不再还原为 Alembic 历史，也不承诺自动接管任意早期数据库形态。

首版只支持三种数据库：

1. 不存在或没有业务表的全新数据库。
2. 没有 `alembic_version`，但结构和数据格式已经符合引入 Alembic 时当前基线的数据库。
3. 已经存在合法 `alembic_version` 的数据库。

不符合当前基线的无版本数据库必须停止启动并提示用户，不能猜测修复或强制 `stamp`。如果以后确实需要兼容某种已发布旧库，再通过经过测试的专用导入工具或明确 migration 处理，不把历史兼容复杂度放进首版。

AIMux 使用 SQLite 保存账号、模型、使用记录和监控记录。代理、超时、重试次数、监控开关和本地令牌保存在用户数据目录的 `config.json`，不属于 Alembic 管理范围；配置格式以后如有不兼容变化，应单独引入 `config_version`。

## 2. 核心原则

- 应用版本与数据库 revision 分开管理，并记录每个应用版本对应的 Alembic head。
- `001_current_baseline` 一经发布不可修改；后续数据库变化从 `002` 开始追加 revision。
- 已发布 migration 只能追加，不能修改、删除、重排或改变既有语义。
- SQLModel 描述当前目标模型，Alembic 保存 schema 演进历史；修改数据库模型必须同时提交 migration。
- 业务层、Service 和 DAO 不执行临时 DDL，也不再通过 `_ensure_columns()` 隐式升级。
- 源码、Windows 打包和 macOS 打包使用同一个项目内 migration runner。
- 迁移失败时停止 API 和监控任务启动，不允许业务代码访问半升级数据库。
- 不自动 downgrade。数据库 revision 高于或不属于当前应用 revision 图时拒绝启动。

## 3. 目录与运行时依赖

Alembic 加入 `pyproject.toml` 的运行时依赖。迁移目录固定为：

```text
migrations/
├── env.py
├── script.py.mako
└── versions/
    ├── 001_current_baseline.py
    ├── 002_next_database_change.py
    └── ...
```

项目内 runner 使用代码构造 `Alembic Config`，动态传入最终 SQLite URL 和 `script_location`，不依赖当前工作目录，也不要求用户安装 Alembic CLI 或提供 `alembic.ini`。

当前 PyInstaller 构建只复制 `assets/`。实施时必须在 `scripts/build.py` 中将 `migrations/` 加入 `--add-data`，runner 使用 `app.utils.resources.resource_path()` 定位源码或打包后的迁移目录。Windows 和 macOS 打包测试都要验证 migration 文件存在且可执行。

## 4. `001_current_baseline` 的定义

`001_current_baseline` 直接创建引入 Alembic 时的当前完整结构，包括：

- `accounts` 表及当前全部字段、CHECK 和索引，其中 `multiplier` 必须存在，范围为 `0.01` 至 `0.30`。
- `models` 表及 `is_default`、唯一约束和索引。
- `usage_records` 表及 `reasoning_effort`、`cached_tokens` 和当前全部索引。
- `monitor_records` 表及当前全部索引。
- 密钥字段继续使用历史列名 `api_key_encrypted`，但数据库内容按当前规则保存明文 TEXT。

基线必须以 `app/models.py` 的当前结构为准。正式接入后，启动流程不再先调用 `SQLModel.metadata.create_all()`，否则空库会在 Alembic 执行 `001` 前提前创建表。

默认模型不写死在 schema migration 中。Alembic 完成并通过校验后，继续调用现有 `seed_defaults()` 做幂等业务初始化。

## 5. 首次启动分类

### 5.1 全新数据库

数据库文件不存在、文件为空，或者仅包含 SQLite 内部表且没有 AIMux 业务表时：

```text
alembic upgrade head
```

当前只有 `001` 时即执行 `base -> 001_current_baseline`，由 Alembic 创建全部业务表、索引和 `alembic_version`。

### 5.2 当前形态的无版本数据库

数据库已有 AIMux 业务表，但没有 `alembic_version` 时，只做当前基线校验，不执行历史修复。校验至少包括：

- 四张业务表均存在。
- 当前全部列存在，列的 NULL 属性和关键默认值符合基线。
- CHECK、UNIQUE 和关键索引符合基线。
- `accounts.api_key_encrypted` 存在，非空密钥以 SQLite TEXT 保存；不接受旧 Fernet BLOB。
- `accounts.multiplier`、`models.is_default`、`usage_records.reasoning_effort` 和 `cached_tokens` 均已存在。
- `PRAGMA integrity_check` 返回 `ok`。

校验通过后先创建一致性备份，再执行：

```text
alembic stamp 001_current_baseline
alembic upgrade head
```

`stamp` 只写版本标记，不修改业务表或数据。校验不通过时停止启动，并提示该数据库不是 Alembic 首版支持的当前形态；禁止调用现有 `_ensure_columns()` 后再强行 stamp。

### 5.3 已有 Alembic 数据库

- 当前 revision 位于本应用 revision 图中且不高于 head：执行 `upgrade head`。
- 当前 revision 等于 head：不迁移、不备份，直接进入正常初始化。
- revision 未知、分叉不受支持或高于本应用 head：停止启动，不自动 stamp、修复或 downgrade。

## 6. 启动升级流程

`configure_database()` 调用项目内 migration runner，顺序如下：

1. 解析 `Settings.resolved_db_path`，创建父目录并取得规范化绝对路径。
2. 获取数据库旁的跨平台迁移锁，例如 `<database>.migrate.lock`，并设置明确等待超时。
3. 在持锁状态下重新识别数据库属于全新、当前无版本或已有 Alembic 三种形态中的哪一种。
4. 若需要执行 migration 或首次 stamp，对已有数据的数据库先创建并校验备份。
5. 按第 5 节执行 `upgrade` 或“校验、stamp、upgrade”。
6. 执行 `PRAGMA integrity_check`，并校验数据库当前 revision 等于打包 head。
7. 创建正常 SQLModel engine，执行 `seed_defaults()`。
8. 释放迁移锁，随后 FastAPI 才接受请求，监控任务才启动。

正式接入后删除 `_ensure_columns()`。`configure_database()` 不再使用 `create_all()` 或临时 `ALTER TABLE` 修复已有库。

文件锁只能协调认识该锁的新版进程。代码还必须处理 SQLite 的 `busy/locked` 错误；不能仅依赖当前端口预检查，因为不同端口的实例可能指向同一个自定义 `db_path`。

## 7. 备份、事务与失败恢复

- 只在 migration 或首次 stamp 会写入已有数据库时创建备份；已在 head 的正常启动不重复备份。
- 使用 Python `sqlite3.Connection.backup()` 或等价 SQLite Backup API，不直接复制可能处于 WAL 状态的主文件。
- 备份放在实际数据库文件旁，兼容自定义 `db_path`，文件名包含 UTC 时间和迁移前 revision 或 `unversioned` 标识。
- 备份必须能够打开并通过 `PRAGMA integrity_check`，否则不得开始写入。
- 默认只保留最近 5 份符合 AIMux 命名规则的迁移备份，不删除当前数据库或未知文件。
- SQLite DDL 和 batch mode 不承诺整个多 revision 升级链原子回滚；最终恢复保证依赖迁移前备份。
- 任一步失败都停止应用启动，保留失败现场、备份和脱敏日志，不自动恢复或继续运行。
- 启动日志记录数据库路径、迁移前 revision、目标 head、失败 revision 和异常摘要，不记录 API 密钥或业务正文。
- 桌面模式显示错误提示和备份/日志位置；`--server-only` 模式写入 `startup-error.log` 并返回非零退出码。

## 8. Schema 与配置职责

- Alembic migration 是数据库演进历史的唯一来源。
- SQLModel metadata 是当前运行时代码期望的目标结构。
- 测试比较 Alembic head 生成的 schema 与 SQLModel metadata，发现表、列、类型、默认值、约束或索引漂移时失败。
- `scripts/schema.sql` 不再作为手工维护的第三份真相：应从 Alembic head 自动导出并校验，或者删除并改为文档说明。
- `config.json` 缺失字段继续由 `Settings` 默认值兼容；配置字段重命名、拆分或语义变化使用独立配置迁移器，不创建 Alembic revision。

## 9. 后续开发规范

从 `001` 发布后，每次数据库变化按以下流程执行：

1. 修改 SQLModel 与业务设计。
2. 新增一个以当前 head 为 `down_revision` 的 migration。
3. 人工审查 upgrade 的数据回填、SQLite batch 表复制、约束和索引。
4. 测试从上一 revision 升级到新 head，并验证数据保留。
5. 测试全新数据库从 `base` 一次升级到新 head。
6. 测试已在 head 的重复启动不会重复修改或备份。
7. 更新应用版本与目标 head 的映射和发布说明。
8. 打包前运行完整测试、migration 测试以及 Windows/macOS 打包产物启动测试。

自动生成 migration 只能作为草稿，不能未经审查直接提交。开发脚本可以重建临时数据库、导出 schema 或校验 revision，但不能直接修改用户业务数据库来代替 migration。

## 10. 测试验收标准

- 不存在和空数据库均可从 `base` 升级到 `head`。
- 当前无版本数据库校验通过后只增加版本标记，不修改账号、密钥、模型和记录数据。
- 缺列、旧密钥 BLOB、异常约束或未知表结构的无版本数据库会明确拒绝，不会被强制 stamp。
- 已升级数据库重复启动不会重复建表、加列、建索引、回填、播种或创建无意义备份。
- 从每一个 Alembic revision 都能连续升级到当前 head，数据不丢失。
- 数据库 revision 高于或不属于当前 revision 图时拒绝启动。
- migration 失败时 API 和监控不会启动，迁移前备份可用于恢复。
- 并发启动同一数据库时只有一个进程迁移，其他进程等待或收到明确错误。
- 覆盖数据库锁定、只读目录、备份失败、损坏库、中文/空格路径和自定义 `db_path`。
- Alembic head schema 与 SQLModel metadata 一致。
- Windows 和 macOS 打包产物包含 Alembic 及所有 migration，并能在没有开发环境的机器上自动升级。

## 11. 实施步骤

### 阶段一：建立当前基线

加入 Alembic 运行时依赖，创建 runner 和 `001_current_baseline`，实现全新数据库升级及 Alembic revision 校验。

### 阶段二：接管当前无版本数据库

实现严格的当前基线校验、SQLite Backup API、首次 `stamp 001`、文件锁、完整性检查和启动错误提示。使用引入 Alembic 前当前代码生成的真实脱敏数据库作为 fixture。

### 阶段三：切换启动与打包流程

删除 `_ensure_columns()` 和启动时 `create_all()`，保留迁移后的 engine 创建及 `seed_defaults()`；将 `migrations/` 加入 PyInstaller，并验证 Windows/macOS 产物。

### 阶段四：从 `002` 开始正常演进

以后所有数据库变化只追加 Alembic revision，并在 README 和发布说明中记录目标 head、迁移摘要、备份位置和失败恢复方式。

## 12. 明确不支持的事项

- 不自动接管 Alembic 引入前的任意历史数据库形态。
- 不迁移或解密旧 Fernet BLOB 密钥。
- 不对校验失败的无版本数据库猜测修复或强制 stamp。
- 不自动 downgrade 高版本数据库。
- 不在客户端启动时下载或执行远程 SQL。
- 不把用户数据库或配置文件打包进安装目录。
- 不要求普通用户安装或运行 Alembic；迁移能力必须随 AIMux 打包产物提供。
