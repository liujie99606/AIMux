# 数据库迁移升级规划

## 1. 背景与目标

AIMux 使用 SQLite 保存账号、模型、使用记录和监控记录。运行配置（代理、超时、监控开关、本地令牌等）保存在用户数据目录的 `config.json`，不属于数据库 schema，不能通过 Alembic 管理；配置格式以后如需迁移，应单独引入 `config_version`。

当前数据库启动流程主要依赖 `SQLModel.metadata.create_all()`，并在 `app/db.py` 中通过 `_ensure_columns()` 补充少量缺失列。这种方式只能处理新增表、简单补列和当前已有的一次列重命名，无法可靠处理字段类型、约束、索引、表重建、数据格式转换以及多版本连续升级。

本规划的目标是：用户从任一明确支持的已发布数据库形态升级时，AIMux 都能在启动阶段自动、安全、可追踪地完成数据库升级，不要求用户安装开发环境或手工执行 SQL。未知或损坏的数据库不得猜测迁移，必须停止启动并保留恢复材料。

## 2. 核心原则

- 应用版本和数据库 revision 分开管理，并维护“应用版本 -> Alembic head revision”映射。
- Alembic `revision` 是不可变标识；文件名可使用递增前缀便于阅读，例如 `002_add_xxx.py`，但不能依赖文件名数字判断版本先后。
- 已发布 migration 只能追加，不能修改、删除或重排；修复已有迁移时新增后续 revision。
- 新库和旧库使用同一个项目内迁移入口，源码、Windows 打包和 macOS 打包不得使用不同逻辑。
- `SQLModel` 描述当前目标模型，Alembic 保存 schema 演进历史；禁止只修改模型而不提交对应 migration。
- 业务层和 DAO 不执行临时 DDL；schema 和持久化数据格式变化必须进入正式迁移。
- 迁移失败时停止 API 和监控任务启动，不允许业务代码访问半升级数据库。
- 不自动 downgrade。应用发现数据库 revision 高于自身打包的 head 时，必须拒绝启动并提示安装更高版本。

## 3. Alembic 目录与打包

Alembic 加入 `pyproject.toml` 的运行时依赖，而不是仅放入 `dev` 依赖。迁移目录固定为：

```text
migrations/
├── env.py
├── script.py.mako
└── versions/
    ├── 001_current_baseline.py
    └── 002_example_future_change.py
```

项目内 runner 使用代码创建 `Alembic Config`，动态传入经过正确转义的 SQLite URL、`script_location` 和连接设置，不依赖当前工作目录，也不要求用户目录存在 `alembic.ini`。

当前 PyInstaller 构建只复制 `assets/`，因此实施时必须在 `scripts/build.py` 中显式将 `migrations/` 加入 `--add-data`，runner 再通过 `app.utils.resources.resource_path()` 定位打包后的迁移目录。Windows 和 macOS 打包测试必须验证 revision 文件真实存在且可执行。

迁移脚本优先使用 Alembic Operations API。SQLite 不支持的删列、改类型、改约束等操作使用 batch mode 重建表，并显式定义复制字段、默认值、约束和索引。自动生成的 revision 只能作为草稿，提交前必须人工审查，不能直接信任 autogenerate。

## 4. 首次接入策略

项目此前没有 Alembic 版本表，也没有足以区分所有数据库形态的正式版本标记，因此不能把历史提交伪装成一组已执行过的 Alembic revision。首次上线采用“当前基线 + 旧库接管”策略：

### 4.1 空数据库

空文件或不存在的数据库直接从 Alembic `base` 执行 `upgrade head`。`001_current_baseline` 创建当前完整表、约束和索引。正式接入后不再先调用 `SQLModel.metadata.create_all()`，避免 Alembic 执行基线时遇到已存在表。

### 4.2 已有 Alembic 版本表

- 当前 revision 等于或早于打包 head：正常执行 `upgrade head`。
- revision 不在本应用 revision 图中，或高于打包 head：停止启动，不尝试 stamp、downgrade 或修复。

### 4.3 无 Alembic 版本表的旧业务库

在任何写操作前读取 `sqlite_master`、`PRAGMA table_info`、索引和约束，生成 schema 指纹。接管器只接受测试覆盖过的已知形态，并完成归一化；不能仅根据“某张表存在”就直接 `stamp head`。

当前至少需要覆盖以下历史差异：

- `models`、`monitor_records` 表是否存在。
- `usage_records.reasoning_effort`、`cached_tokens` 是否存在。
- `models.is_default` 是否存在。
- `accounts.multiplier` 是否存在，并为旧数据回填 `0.10`。
- 密钥列是 `api_key` 还是历史名称 `api_key_encrypted`。
- `api_key_encrypted` 的 SQLite 存储类型和内容是旧 Fernet BLOB 还是当前明文 TEXT。
- 当前模型要求的表、列、NOT NULL、默认值、CHECK、UNIQUE 和索引是否完整。

接管流程必须是：识别已知形态 -> 创建备份 -> 执行归一化 -> 校验数据与 schema -> `stamp 001_current_baseline` -> 再执行后续 `upgrade head`。如果指纹未知、关键表缺失但又存在业务数据、密钥无法转换或校验失败，立即停止启动，不得强行 stamp。

首次接入完成后删除 `_ensure_columns()`。旧库接管代码只负责没有 `alembic_version` 的历史数据库，不能继续承担未来 schema 变化。

## 5. 历史密钥数据迁移

早期版本把 `accounts.api_key_encrypted` 保存为与当前机器信息绑定的 Fernet BLOB；当前版本保留该历史字段名，但内容是明文字符串。接管器必须把这项数据格式变化作为正式迁移处理，不能只修改 SQL 列类型或列名。

- `api_key` 明文列无损重命名为 `api_key_encrypted`。
- SQLite 值为 TEXT 时按当前明文处理，不重复解密。
- SQLite 值为 BLOB 且符合旧格式时，使用当时发布版本完全一致的密钥派生和 Fernet 算法解密，再写回 TEXT。
- 迁移期必须保留旧解密实现及其运行时依赖，直到明确不再支持相应历史版本。
- 解密只能在原加密机器环境可靠完成；换机后无法解密时应停止迁移并给出重新录入密钥或回原机器升级的提示。
- 任一非空密钥转换失败时整次接管失败，不能把密文误写成可用明文，也不能跳过该账号。
- 日志、异常、备份清单和测试输出都不得包含密钥原文或密文。

验收时既要验证密钥值可被业务代码直接使用，也要验证 API 只通过 `api_key` 对外返回，不暴露内部历史列名。

## 6. 启动升级流程

`configure_database()` 调用项目内迁移 runner，整体顺序如下：

1. 解析 `Settings.resolved_db_path`，创建父目录并取得规范化绝对路径。
2. 获取数据库旁的跨平台迁移锁，例如 `<database>.migrate.lock`；锁等待必须有明确超时。
3. 在持锁状态下重新检测数据库，识别空库、Alembic 库或无版本旧库。
4. 若无待执行 migration 且无需旧库接管，跳过备份和升级。
5. 对有数据且需要写入的数据库，使用 SQLite Backup API 创建一致性备份；备份成功并校验后才能迁移。
6. 旧库按第 4、5 节执行接管；已有 Alembic 库执行 `upgrade head`。
7. 执行 `PRAGMA foreign_key_check` 和 `PRAGMA integrity_check`，并校验关键表、列、约束、索引与预期 head 一致。
8. 创建正常 SQLModel engine，执行默认模型播种等幂等业务初始化。
9. 释放迁移锁，随后 FastAPI 才可接受请求，后台监控任务才可启动。

文件锁用于协调新版 AIMux 进程；旧版本不认识该锁，因此迁移过程还必须正确处理 SQLite 的 `busy/locked` 错误并停止启动。不同端口启动的多个实例也可能指向同一个自定义 `db_path`，不能只依赖端口预检查防止并发迁移。

## 7. SQLite 事务、备份与恢复边界

SQLite DDL、Alembic batch mode、PRAGMA 和多 revision 升级不能承诺整个升级链一定自动回滚到升级前状态。因此恢复保证以迁移前一致性备份为准：

- 单个 revision 尽量在事务中执行，但文档和 UI 不宣称整个升级链可原子回滚。
- 使用 Python `sqlite3.Connection.backup()` 或等价 SQLite Backup API，不直接复制可能处于 WAL 状态的主文件。
- 备份放在实际数据库文件旁，适配用户自定义 `db_path`；文件名包含 UTC 时间戳和迁移前 revision/schema 标识。
- 备份创建后必须能打开并通过 `PRAGMA integrity_check`，否则不得开始迁移。
- 迁移失败时停止启动，保留原库失败现场、迁移前备份和脱敏错误日志，由用户选择恢复。
- 默认保留最近 5 份迁移备份；只删除匹配 AIMux 备份命名规则的旧文件，绝不能删除当前数据库或未知文件。
- 迁移前检查目录可写性和可用磁盘空间；无法可靠判断空间是否足够时，至少要捕获备份/写入失败并保持原库不被继续修改。
- 第一阶段只提供向前迁移和备份恢复，不实现自动 downgrade。

启动错误日志至少记录数据库绝对路径、迁移前 revision/schema 指纹、目标 head、失败 revision、异常类型和脱敏摘要。桌面 UI 应提示备份路径和 `startup-error.log` 路径；`--server-only` 模式应写日志并返回非零退出码。

## 8. Schema 与配置的职责边界

- Alembic revision 是数据库演进历史的唯一来源。
- SQLModel 模型是当前运行时代码期望的目标结构。
- 测试必须比较 Alembic head 生成的 schema 与 SQLModel metadata，发现列、类型、默认值、约束或索引漂移时失败。
- `scripts/schema.sql` 不再手工维护为第三份真相：应由 Alembic head 自动导出并通过测试校验，或者删除并改为文档指向迁移命令。
- `config.json` 字段继续由 `Settings` 默认值兼容缺失字段。发生重命名、拆分或语义变化时，使用独立 `config_version` 和配置迁移器，不能创建 Alembic revision。
- `monitoring_enabled`、代理设置、超时、重试次数和本地令牌均属于配置，不进入 SQLite migration。

## 9. 开发与发布规范

以后涉及数据库的需求按以下流程执行：

1. 确认需求属于数据库 schema/持久化数据格式，还是 `config.json` 配置格式。
2. 修改 SQLModel 和业务设计，同时新增 Alembic revision；禁止只改模型或 `_ensure_columns()`。
3. 人工审查 upgrade 中的数据回填、SQLite batch 表复制、约束和索引重建。
4. 为 revision 增加空库、从上一 revision 升级、数据保留、重复启动和失败恢复测试。
5. 使用已发布版本生成的脱敏 SQLite fixture 验证连续升级，不用临时手写的简化表代替全部历史样本。
6. 更新应用版本与目标 Alembic head 的映射及发布说明。
7. 打包前运行完整测试、迁移测试和打包产物启动迁移测试。
8. 提交 migration、模型、测试和文档，禁止提交真实用户数据库或密钥。

开发环境可以提供重建临时数据库、导出 schema 和校验 revision 的脚本，但不能直接修改用户业务数据库来代替 migration。手工 SQL 只能作为明确记录的故障恢复工具。

## 10. 测试验收标准

- 不存在的数据库和空数据库均可从 `base` 升级到 `head`。
- 每种明确支持的无版本旧库指纹都能接管，账号、明文密钥、状态、倍率、模型、使用记录和监控记录不丢失。
- 旧 Fernet 密钥能在原机器环境转换；错误密文和换机无法解密会安全停止，不会泄漏或破坏密钥。
- 已升级数据库重复启动不会重复加列、建索引、回填或覆盖用户数据。
- 数据库 revision 高于或不属于当前 revision 图时拒绝启动。
- migration 中途异常不会启动 API；迁移前备份能够恢复并正常启动。
- Alembic head schema 与 SQLModel metadata 在表、列、类型、默认值、约束和索引方面一致。
- 并发启动同一数据库时只有一个新版本进程迁移，其他进程等待或收到明确错误。
- 覆盖数据库锁定、只读目录、磁盘写入失败、损坏库、中文/空格路径和自定义 `db_path`。
- Windows 与 macOS 打包产物都包含 Alembic 及所有 revision，并能在无开发环境机器上自动升级。
- 迁移完成后默认模型播种、配置读取、API、调度和监控测试通过。

## 11. 实施阶段

### 阶段一：盘点历史数据库形态

建立应用版本、Git 提交、数据库 schema 指纹和密钥格式清单；收集或生成脱敏历史 SQLite fixture。当前仓库没有可直接依赖的发布 tag，因此必须先明确“支持哪些历史形态”，不能笼统承诺所有未知数据库。

### 阶段二：迁移基础设施和当前基线

加入 Alembic 运行时依赖，建立 runner、`001_current_baseline`、动态 URL、资源定位、文件锁、SQLite Backup API、完整性校验和启动错误提示；修改 PyInstaller 资源收集；补充空库、重复启动和打包产物测试。

### 阶段三：旧库接管

实现 schema 指纹识别，覆盖 `_ensure_columns()` 当前所有兼容项以及历史密钥转换。验证后删除 `_ensure_columns()` 和启动时 `create_all()`，未知 schema 一律安全停止。

### 阶段四：后续 revision 与发布运维

后续数据库变化只追加 Alembic revision。README 和发布说明记录应用版本、目标 head、迁移摘要、备份位置和失败恢复步骤，并将 schema 漂移检查加入发布流程。

## 12. 暂不实施的事项

- 不在客户端启动时下载或执行远程 SQL。
- 不对未知 schema 自动猜测、强制 stamp 或删除数据。
- 不在没有一致性备份的情况下重写旧表。
- 不自动 downgrade 高版本数据库。
- 不把用户数据库或配置文件打包进安装目录。
- 不要求普通用户安装或运行 Alembic；迁移能力必须随 AIMux 打包产物提供。
