# 数据库迁移升级规划

## 1. 背景与目标

AIMux 使用 SQLite 保存账号、模型、使用记录、监控记录和运行配置。当前启动流程主要依赖 `SQLModel.metadata.create_all()`，并在 `app/db.py` 中通过 `_ensure_columns()` 补充少量缺失列。这种方式只能覆盖“新增表”和“简单新增列”，无法可靠处理列重命名、字段类型变化、约束/索引变化、数据回填以及多版本连续升级。

本规划的目标是：用户从任意已发布版本升级到新版本时，程序能够自动、安全、可追踪地完成数据库升级，不要求用户安装开发环境，也不要求 Codex 或人工直接修改用户数据库。

## 2. 核心原则

- 应用版本和数据库版本分开管理。应用版本例如 `1.1.3`，数据库版本使用单调递增整数，例如 `4`。
- 每一次数据库结构或数据格式变更都必须新增一个不可修改的迁移脚本。
- 已发布迁移只追加，不修改、不删除；修复迁移问题时新增后续迁移。
- 新用户和旧用户使用同一套迁移入口，禁止“开发环境一套、打包环境另一套”。
- 业务代码不直接执行临时 `ALTER TABLE`；所有 schema 变化都写入正式迁移。
- 迁移过程必须可观测：记录当前版本、目标版本、执行结果和失败原因。
- 迁移失败时宁可停止启动，也不能在不完整 schema 上继续运行并破坏数据。

## 3. 推荐目录与版本表

建议引入 Alembic（或等价的轻量迁移器）。如果暂不引入第三方框架，也必须保持相同的版本化约定：

```text
migrations/
├── README.md
├── runner.py
└── versions/
    ├── 001_initial_schema.py
    ├── 002_add_usage_token_fields.py
    ├── 003_add_monitor_records.py
    └── 004_add_monitoring_enabled.py
```

数据库中维护迁移版本表（Alembic 默认表名为 `alembic_version`），只保存当前已成功执行的版本号。每个迁移脚本至少包含：版本号、前置版本、升级函数；如确实有需要，再提供降级函数。

## 4. 启动时的升级流程

`configure_database()` 应调整为以下顺序：

1. 解析最终数据库路径并创建父目录。
2. 获取 SQLite 文件锁，避免多个 AIMux 进程同时迁移同一个数据库。
3. 检测数据库是否存在；首次安装创建空库，已有数据库读取当前迁移版本。
4. 在执行首个迁移前创建带时间戳的备份，例如 `aimux.db.backup-20260810-120000`。
5. 按版本号顺序执行所有未执行迁移，每个迁移在事务中完成。
6. 每个迁移成功后更新版本表；任一步失败则回滚当前事务并停止应用启动。
7. 迁移完成后再执行默认模型播种等非破坏性初始化。
8. 建立 SQLModel engine 和正常服务生命周期。

迁移应在 FastAPI 接受请求前完成。升级期间不应允许 API 请求读写半升级数据库。

## 5. 现有逻辑的迁移安排

当前 `_ensure_columns()` 中的补列逻辑不能继续作为长期的隐式升级机制，应拆成有明确版本的迁移：

- 现有基础表和索引整理为基线迁移 `001_initial_schema`。
- `usage_records.reasoning_effort`、`cached_tokens` 等历史补列整理为独立迁移。
- `models.is_default` 整理为独立迁移。
- `monitor_records` 和监控设置字段分别使用独立迁移。

正式迁移器上线后，删除或收缩 `_ensure_columns()`，避免同一个变更同时由两套逻辑执行。对于已经存在的旧数据库，需要先定义一个明确的基线版本，再从基线继续升级，不能假定所有用户数据库都来自当前开发分支。

## 6. 备份、失败与恢复

- 备份文件和 SQLite 主库放在同一用户数据目录，文件名包含 UTC 时间戳。
- 备份前执行 SQLite checkpoint；复制失败时不得开始迁移。
- 迁移成功后保留最近若干份备份，清理策略必须按明确数量或天数执行，不能删除当前数据库。
- 迁移失败时保留失败现场和备份，日志中记录：数据库路径、当前版本、目标版本、迁移文件、异常摘要。
- UI/启动日志应提示“数据库升级失败，请使用备份恢复”，不能静默忽略异常。
- 第一阶段只要求向前迁移和备份恢复；不建议为了形式实现未经验证的自动 downgrade。

## 7. 开发与发布规范

以后涉及数据库的需求必须按以下流程执行：

1. 先修改模型/业务设计，再新增迁移脚本。
2. 为迁移脚本补充旧库升级测试、重复执行测试和数据保留测试。
3. 在全新数据库上运行完整迁移，确认 schema 与 SQLModel 模型一致。
4. 使用真实或脱敏的历史数据库副本验证连续升级，例如 `1.0.2 -> 1.1.3`。
5. 打包前运行全量测试和迁移测试；打包产物启动时也必须自动执行迁移。
6. 提交迁移文件和对应文档，禁止提交用户数据库文件。

开发环境可以提供“重建临时数据库”脚本，但不得通过 Codex 直接修改业务数据库来代替迁移。任何需要手工执行的 SQL 都只能作为故障恢复工具，并且必须记录在运维文档中。

## 8. 测试验收标准

- 全新数据库可从空库一次迁移到当前版本。
- 每个支持的旧版本都能按顺序升级到当前版本，数据、密钥密文、账号状态和使用记录不丢失。
- 已执行迁移重复启动不会重复加列、重复建索引或覆盖数据。
- 迁移中途异常会回滚当前迁移，应用不会在半升级状态下启动。
- 迁移前备份可用于手工恢复，恢复后 AIMux 能正常启动。
- 多进程同时启动同一数据库时只有一个进程执行迁移，另一个等待或收到明确失败提示。
- 迁移完成后默认模型播种、配置读取和现有 API 测试全部通过。

## 9. 实施阶段

### 阶段一：迁移基础设施

引入迁移工具或实现最小 runner、版本表、文件锁、备份和启动错误提示；补充空库与重复启动测试。

### 阶段二：整理历史兼容逻辑

把 `_ensure_columns()` 中已有变更转换为正式迁移，定义旧库基线版本，验证历史数据库升级路径。

### 阶段三：接入后续功能

监控、代理、Token 字段等以后所有数据库变化只通过新增迁移交付，并在发布检查中强制执行迁移测试。

### 阶段四：发布与运维

在 README 和发布说明中记录应用版本、数据库目标版本、迁移摘要、备份位置及失败恢复步骤。

## 10. 暂不实施的事项

- 不在客户端启动时自动下载或执行远程 SQL。
- 不在没有备份的情况下自动删除旧列或重写整张表。
- 不把数据库文件打包进安装目录；用户数据继续存放在系统用户数据目录。
- 不要求普通用户安装 Python、Alembic 或其他开发依赖。
