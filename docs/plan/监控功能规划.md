# 账号监控功能规划

## 1. 目标与边界

监控用于持续观察账号是否能够正常完成一次最小请求，并在桌面端用最近结果展示账号的可用性趋势。监控是 AIMux 启动后的后台任务，不依赖用户打开“监控”页面。

本期固定每 2 分钟执行一轮，每轮只检查当前状态为“启用”（`active`）的账号。设置中的“开启账号监控”默认开启，用户关闭后不再执行监控检查。监控成功优先级 `+1`，最高为 `6`；失败优先级 `-1`，最低为 `0`。监控不改变手动启用/禁用状态、最近错误、测试成功模型、真实请求统计或 Token 累计。

监控不负责自动修复账号、不替用户切换账号、不对失败结果重试，也不保存上游响应正文或 API Key。

## 2. 执行周期与生命周期

### 2.1 任务启动

- FastAPI 应用完成启动并开始接受请求后，创建一个独立的 asyncio 后台任务。
- 仅当 `monitoring_enabled = true` 时执行监控；默认值为 `true`。
- 任务首次启动后立即执行一轮，之后每隔 120 秒执行一轮。
- 每轮开始时重新查询 `accounts.status = 'active'`，不使用启动时缓存；账号被禁用后，下一轮不再检查。
- 应用关闭时取消并等待后台任务，不能遗留未关闭的 HTTP 客户端、响应或数据库会话。

监控任务属于后端服务生命周期，不放到 PySide6 主线程，也不由监控页面的定时器驱动。页面关闭或切换不会停止监控。

### 2.2 并发与防重入

- 一轮中的账号检查使用有上限的并发，建议初始并发上限为 5，避免账号数量较多时串行耗时过长。
- 下一轮不能与上一轮重叠；若上一轮仍在执行，跳过本次 tick，并记录调度日志。
- 每个账号每轮只发起一次上游请求，不使用 `request_retry_attempts`，监控结果应反映这一轮的单次连通性。

### 2.3 监控开关

设置页增加“开启账号监控”复选框，对应配置字段 `monitoring_enabled: bool = true`：

- 默认开启，首次安装无需用户配置即可开始监控。
- 保存为关闭后立即停止安排新的监控轮次；已经发出的本轮请求允许正常完成并保存结果，不强行中断网络请求。
- 关闭期间不发送 ping、不创建新的监控记录，已有历史记录继续保留并可查看。
- 重新开启后立即执行一轮，然后恢复每 120 秒一次的周期。
- 开关属于运行时配置，保存后当前进程立即生效，不要求重启 AIMux。
- 可增加环境变量 `AIMUX_MONITORING_ENABLED`，其布尔解析规则与现有配置一致。

调度器应通过可唤醒的事件或配置变更通知响应开关，不能只在固定 `sleep(120)` 结束后才发现设置变化。

## 3. Ping 请求规则

### 3.1 模型选择

每个账号按账号协议类型选择模型维护中的“测试默认”模型（`CatalogModel.is_default = 1`）：

- OpenAI 账号使用 OpenAI 类型默认模型。
- Anthropic 账号使用 Anthropic 类型默认模型。
- 若该类型没有默认模型，写入一次失败记录，错误码为 `monitor_model_unavailable`，不向上游发送请求；正常启动流程应保证每种类型有默认模型。

### 3.2 请求内容

请求应复用当前账号测试的协议、认证头、上游代理和超时构造，但不能复用会改变账号状态的测试结果处理：

- 消息内容固定为 `ping`。
- 请求使用最小输出限制，避免监控产生不必要的消耗。
- OpenAI 请求附带 `reasoning_effort: "low"`。
- Anthropic 不发送 OpenAI 专用的 `reasoning_effort` 字段，使用该协议支持的最小请求格式。
- 端点按账号类型选择 `/v1/chat/completions` 或 `/v1/messages`。

建议抽取一个“构造并发送 ping”的无副作用服务函数，由人工测试和监控共同调用；人工测试和监控均在外层执行各自独立的优先级变更规则，再保存监控记录。

## 4. 结果与数据模型

监控记录使用独立的 `monitor_records` 表，不写入 `usage_records`。这样使用记录仍只代表客户端真实请求，监控失败也不会被调度重试逻辑误认为真实请求失败。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `account_id` | 被检查账号 ID，保留历史关联 |
| `account_name` | 检查时的账号名称快照 |
| `account_type` | `openai` 或 `anthropic` |
| `model` | 本次实际使用的默认模型 |
| `checked_at` | 检查开始时间，使用 UTC |
| `duration_ms` | 从发起到收到完整响应的耗时 |
| `success` | HTTP 2xx 且响应正常为成功 |
| `status_code` | 上游 HTTP 状态码，可为空 |
| `error_code` | 统一错误码，可为空 |
| `error_message` | 截断后的错误信息，可为空 |

成功和失败都必须写入一条记录。监控不能调用人工测试或真实请求的结果记录方法；应使用监控专用优先级规则，成功 `+1` 且最高为 `6`，失败 `-1` 且最低为 `0`。监控不得修改 `last_error_*`、`total_requests` 或 `total_tokens`。

错误分类沿用现有测试/转发错误归一规则：连接异常、超时、非 2xx、响应解析失败分别保留明确错误码。错误正文只保存有限长度文本，不保存完整响应。

## 5. 监控查询 API

增加受本地令牌保护的管理接口：

`GET /api/monitor/records?limit=30`

接口只返回当前仍为 `active` 的账号。返回按账号分组，每个账号的记录最多 30 条，按时间从旧到新排列，便于前端从左到右绘制“过去 → 现在”的状态条。建议响应结构：

```json
{
  "items": [
    {
      "account_id": "...",
      "account_name": "账号 A",
      "account_type": "openai",
      "records": [
        {"checked_at": "...", "success": true, "duration_ms": 820, "status_code": 200},
        {"checked_at": "...", "success": false, "duration_ms": 30000, "error_code": "upstream_timeout"}
      ]
    }
  ]
}
```

`limit` 默认 30，服务端限制在 1 至 30；账号没有监控记录时返回空数组。停用账号不出现在监控页面，但其历史记录不因停用而删除。

## 6. 监控页面

新增独立的“监控”导航页面：

- 只显示当前启用账号，每个账号一行。
- 展示账号名称、协议类型、监控模型、最近检查时间和最近耗时。
- 中间展示固定 30 个状态格，按时间从左到右排列：成功为绿色、失败为红色、没有数据为灰色。
- 鼠标悬停状态格显示检查时间、耗时、状态码和错误信息；失败信息使用深色警示色。
- 页面进入时立即查询；页面打开期间可用 30 秒 UI 定时刷新，不负责触发监控任务。
- 页面展示当前监控开关状态；关闭时显示“监控已关闭”，但仍允许查看已有的最近记录。
- 账号被停用后下一次刷新消失，重新启用后重新出现并显示仍保留的最近记录。

## 7. 实现拆分

1. 抽取无副作用的 ping 请求构造/发送函数，保留现有人工测试接口行为。
2. 新增 `MonitorRecord` 模型、DAO、service 和数据库启动建表/旧库兼容逻辑。
3. 在 `Settings`、设置 schema 和设置页面增加默认开启的 `monitoring_enabled`，保存后通知当前调度器。
4. 新增监控调度器，在 FastAPI lifespan 中启动、停止、响应开关和防重入。
5. 新增监控查询 controller 及响应 schema，查询只关联启用账号并限制每账号 30 条。
6. 新增监控页面、状态格组件和页面刷新逻辑。
7. 补充 API、调度、开关即时生效、数据不影响账号状态、每账号 30 条和页面渲染数据测试。

## 8. 验收标准

- AIMux 启动后能立即完成一轮，随后约每 120 秒执行一次。
- 监控默认开启；关闭后不再产生新记录，重新开启后立即开始新一轮，整个过程无需重启。
- 启用账号每轮恰好产生一条成功或失败记录；停用账号不产生新记录。
- OpenAI/Anthropic 均使用对应类型的默认模型；OpenAI 使用 `reasoning_effort=low`。
- 监控成功后优先级 `+1` 且最高为 `6`，失败后优先级 `-1` 且最低为 `0`；账号状态、最近错误和真实请求统计完全不变。
- 一个账号查询结果最多 30 条，状态条顺序为旧到新，成功/失败颜色与结果一致。
- 服务关闭后后台任务和 HTTP 资源均被释放，测试和真实请求不再出现重复监控任务。
