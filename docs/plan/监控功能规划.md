# 账号监控功能规划

## 1. 目标和边界

监控用于持续观察启用账号是否能完成一次最小请求，并在页面展示最近结果趋势。它是 Rust 后端的后台任务，不依赖用户是否打开监控页面。

默认每 2 分钟执行一轮，每轮只查询当前启用账号。监控不负责真实请求重试，不保存 API Key 或完整上游响应正文。

## 2. 生命周期

- Axum 网关初始化成功后启动独立 Tokio 任务。
- 任务首次启动立即执行一轮，之后按配置间隔执行。
- 每轮开始重新查询账号，禁用账号不会在下一轮继续测试。
- 应用退出时取消并等待任务，释放 Reqwest 响应和数据库连接。
- 设置关闭监控后立即停止新的轮次；重新开启后立即执行一轮。

## 3. 调度和结果

- 每轮最多 5 个并发账号测试，避免账号数量过多拖慢整个周期。
- 同一轮不允许重入；上一轮未结束时跳过 tick 并记录日志。
- 每个账号每轮只请求一次，不使用真实请求的总重试次数。
- 成功时优先级 0 至 5 加 1，6 至 9 保持不变；失败时减 1，最低为 0。
- 每轮按协议选出成功的最低倍率账号，并将其优先级设置为 9；正式取号按优先级降序、倍率升序。
- 监控请求使用账号的测试默认模型或协议默认模型，并遵循账号模型映射。

## 4. 页面展示

管理页面通过 `/api/monitor` 查询启用账号的最近 30 次检测结果，表格展示账号、协议、倍率、平均耗时和最近 30 次状态格。成功为绿色，失败为红色，耗时超过 20 秒为黄色；失败优先级高于耗时颜色。

页面刷新只重新请求数据，不启动或停止后台监控任务。切换菜单、筛选和浏览器刷新不会改变监控生命周期。

## 5. 验证

- 验证开关保存后当前进程立即生效。
- 验证 2 分钟周期和首次立即执行。
- 验证一次失败不会影响后续账号测试。
- 验证成功/失败优先级边界、倍率比较、模型映射和数据库写入。
- 验证页面只显示最近 30 条，不因数据量增加而返回全部历史记录。
