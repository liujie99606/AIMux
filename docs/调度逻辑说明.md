# 调度逻辑说明

## 1. 账号候选范围

每次请求都从数据库实时读取候选账号，不使用启动时缓存。请求协议决定账号类型：OpenAI 只从 `type=openai` 的账号中选择，Anthropic 只从 `type=anthropic` 的账号中选择；`status=disabled` 的账号永远不会参与调度。

账号还要满足模型匹配条件：如果账号没有显式支持模型列表，视为通配账号；如果有列表，则请求模型必须在列表中。候选账号排序为“显式声明当前模型的账号优先 → 优先级降序 → 倍率升序 → 名称升序 → ID 升序”。因此调度排序和账号管理列表排序不同：调度会优先选择明确支持当前模型的账号，并在优先级相同时优先选择倍率更低的账号。

## 2. 非流式请求流程

1. 从请求体读取 `model` 和 `reasoning_effort`，生成本次请求的 `trace_id`。
2. 读取当前配置的总尝试次数，循环直到成功、没有候选账号或达到上限。
3. 每次循环重新选择当前最高优先级的可用账号，并将该账号 `total_requests + 1`、更新最近使用时间。选号始终使用客户端请求的模型名。
4. 选中账号后，读取该账号的模型映射；精确匹配时只在本次上游请求副本中替换 `model`，未命中则保持客户端模型。每次重试都会按新选中的账号重新解析映射。
5. 向账号的原始协议端点发起请求。OpenAI 和 Anthropic 的 URL、认证头和允许透传的协议头分别按类型处理。
6. 上游返回 2xx 时，账号优先级加 1、清除最近错误，解析响应中的 Token 用量，写入一条成功 `UsageRecord` 并返回原响应。
7. 上游返回非 2xx 或发生超时/连接异常时，账号优先级减 1，保存最近错误，写入一条失败 `UsageRecord`，然后回到第 2 步。
8. 没有账号或达到总尝试次数时，返回最后一次失败的协议格式化错误。

“总尝试次数”是整个客户端请求的上限，不是每个账号各自的上限，也不是失败账号排除名单。账号降级后可能仍然是最高账号，因此在其他账号超过它之前仍可能被再次选择。

## 3. 流式请求流程

流式请求在向客户端输出首块前允许重试。每次尝试先按客户端模型选号，再为选中账号单独解析模型映射、复制请求体并打开上游流；在 `first_token_timeout_seconds` 内等待第一个块。打开失败、非 2xx 或首块超时都会降级账号、记录失败并选择下一个候选账号。

首块已经发给客户端后不再切换账号或重放请求。后续读取异常只记录该流失败；流正常结束时解析 SSE 中的 usage，并在流结束后用新数据库会话写入成功记录。

## 4. 优先级变化

| 事件 | 变化 |
|---|---:|
| 真实请求成功 | `+1` |
| 真实请求失败 | `-1` |
| 连接测试成功 | `+3` |
| 连接测试失败 | `-1` |
| 页面快捷操作 | `+4` 或 `-4` |

优先级始终限制在 0-9。测试结果不会改变人工启用/停用状态；真实请求失败也不会自动停用账号。

## 5. 使用记录语义

调度器对每一次上游尝试调用 `_write_usage`，所以重试不会覆盖之前的失败。相同客户端请求的记录共享 `trace_id`，`attempts` 分别为 1、2、3……。最终成功时，最后一条记录为成功；最终失败时，所有尝试记录均为失败。无账号可选时还会写入一条 `account_id` 为空的最终失败记录。`UsageRecord.model` 始终记录客户端请求模型，不会被账号模型映射改写。
