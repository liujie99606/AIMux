# AIMux Rust 重构技术栈分析

## 1. 文档目的

本文为 AIMuxRust 重构的技术选型和落地依据。重构目标不是简单替换桌面 UI，而是将现有 Python/PySide6/FastAPI 应用迁移为：

- Vue 3：页面和交互层。
- Vite：前端开发、构建和资源管理。
- Element Plus：桌面端管理界面组件库。
- Pinia：前端共享状态和缓存。
- Tauri 2：桌面窗口、安装包和前端与 Rust 的桥接。
- Rust：本地 HTTP 网关、调度、监控和数据访问。
- SQLite：本地持久化数据库。

重构期间保留现有 Python 版本作为行为参照。Rust 版本完成同等功能并通过验证后，再考虑停止维护 Python 版本。

## 2. 现有系统基线

AIMux 当前是一个本地运行的 AI 中转聚合网关：桌面程序启动本地 API 服务，客户端通过 `http://127.0.0.1:7789/v1` 请求，服务按协议、账号状态、优先级和倍率选择上游并执行失败重试。

现有能力包括：

- OpenAI 和 Anthropic 原生协议兼容，包括非流式、SSE 流式及相关辅助接口。
- 账号增删改查、启用/禁用、优先级、倍率、支持模型、测试默认模型和模型映射。
- 每次上游尝试写入使用记录，记录 Token、缓存 Token、首 Token 耗时、总耗时和失败信息。
- 账号监控、最近 30 次检测结果、监控优先级调整和平均耗时。
- 使用记录分页查询、数据统计、历史数据清理和详情查看。
- 设置监听地址、端口、超时、重试、代理、本地令牌和监控开关；数据库固定使用数据目录下的 `aimux.db`。

这些行为属于兼容性约束，Rust 版本必须以现有 API 和数据库字段为迁移基线，而不是重新设计一套不兼容协议。

## 3. 总体架构

```text
外部 AI 客户端
        |
        | OpenAI/Anthropic HTTP API
        v
Rust HTTP 网关（axum + tokio）
        |
        +-- 调度服务：pick_one、优先级、倍率、模型映射、重试
        +-- 上游客户端：reqwest、代理、超时、SSE 转发
        +-- 监控任务：tokio interval + 并发限制
        +-- 使用记录服务：每次尝试落库、Token 解析
        +-- SQLite 数据访问和结构兼容检查
        |
Tauri 2 主进程
        |
        +-- Vue 3 管理界面（Element Plus + Pinia）
        +-- Tauri commands：窗口、文件目录、系统能力等桌面功能
```

### 3.1 为什么仍然需要 Rust HTTP 服务

Tauri command 只适合桌面前端调用，外部的 CC Switch、OpenAI SDK 或其他电脑无法直接调用它。AIMux 的核心产品是本地 HTTP 网关，因此必须在 Tauri 进程内启动 axum/Hyper HTTP 服务，并继续监听配置中的地址和端口。

前端管理页面优先通过 HTTP 管理 API 访问 Rust 服务，必要的桌面能力（打开数据目录、检查更新、窗口控制）再使用 Tauri command。这样可以复用网关 API，也便于后续 `--server-only` 或无界面模式。

## 4. 技术选型

### 4.1 Rust 后端

| 领域 | 建议技术 | 选择理由 |
| --- | --- | --- |
| 异步运行时 | Tokio | 支持并发上游请求、定时监控和流式响应 |
| HTTP 路由 | Axum | 与 Tokio 生态一致，类型安全，适合管理 API 和 `/v1` |
| HTTP 客户端 | Reqwest | 支持连接池、代理、超时、SSE 字节流和 TLS |
| JSON | Serde/serde_json | 请求、响应和数据库 JSON 字段统一序列化 |
| 数据库 | SQLx + SQLite | 异步访问和编译期查询检查；本次直接兼容现有库，不执行结构迁移 |
| 错误处理 | thiserror + anyhow | 业务错误可分类，应用边界保留上下文 |
| 日志 | tracing + tracing-subscriber | 便于排查上游超时、重试和监控任务 |
| 并发控制 | tokio::sync::Semaphore | 限制监控和上游请求的并发量 |
| 时间 | chrono/time | 统一 UTC 存储、按本地时区展示 |

不建议使用 Rust 嵌入 Python 或在 Tauri 中继续启动 Python 子进程作为长期方案，这会保留 Python 运行时、打包慢和跨平台兼容等原问题。

### 4.2 前端

- Vue 3 使用 Composition API 和 `<script setup>`。
- Vite 负责开发服务器和生产资源构建。
- Element Plus 负责表格、分页、表单、弹窗、下拉框和通知。
- Element Plus Icons 负责按钮、菜单和状态操作图标，避免重复维护图标资源。
- Pinia 只保存跨页面状态：设置、账号筛选、模型目录、当前服务状态等；页面临时表单状态留在页面组件内。
- 使用少量自定义 SCSS/CSS 统一紧凑桌面端的表格行高、输入框高度、页面间距、字体和主题变量。
- 不额外引入 Tailwind 等第二套完整 UI 样式体系，避免与 Element Plus 产生样式覆盖和设计规范分裂。
- 可选引入 `normalize.css` 统一基础样式，使用 `sass` 管理主题变量。
- `src/api/` 统一封装 HTTP 请求，禁止在组件中散落 URL 和响应解析。
- `src/types/` 定义与 Rust API 对应的 TypeScript 类型，避免 `any` 扩散。

### 4.3 Tauri 2

Tauri 只承担桌面壳和系统集成：窗口尺寸、菜单、打开本地目录、自动更新、应用退出和打包。业务调度、数据库和网络请求放在 Rust 服务层，避免把业务逻辑写进 command 导致两套调用路径。

### 5.1 后端分层职责

- `controller`：定义 HTTP 路由处理函数，解析路径、查询参数、请求体和认证信息，调用 service 并转换响应；不直接编写 SQL。
- `service`：承载调度、重试、模型映射、优先级、监控和统计等业务规则；通过 dao 读写数据。
- `dao`：封装 SQLx 查询、分页、筛选、排序和事务；不决定业务策略。
- `model`：对应 SQLite 持久化实体和领域对象。
- `schema`：定义 API 请求/响应 DTO、分页结构和校验规则，避免把数据库实体直接暴露给客户端。
- `gateway`：专门处理 OpenAI/Anthropic 兼容协议、SSE 和协议头，不绕过 service 调度层。
- `upstream`：封装 reqwest 客户端、代理、超时、TLS 和上游错误分类。
- `database`：负责连接池、WAL 配置、表结构检查和只读兼容性校验，不负责修改现有表结构。
- `background`：负责监控等生命周期任务的启动、停止和配置变更唤醒。

依赖方向固定为：`controller/gateway -> service -> dao -> database`。service 可以使用 model 和 upstream，但 dao 不应反向依赖 controller；这样便于对调度逻辑做单元测试，也避免管理 API 和网关 API 出现两套规则。

### 5.2 前端分层职责

- `api`：按业务模块封装管理 API 请求，统一处理认证、分页参数、错误和响应类型。
- `stores`：保存跨页面共享状态和刷新动作，不在 store 内直接操作组件。
- `pages`：组合页面布局、筛选条件、表格和弹窗，负责页面级加载状态。
- `components`：提供可复用的表格、状态标签、分页、表单和监控状态格。
- `types`：维护 TypeScript 接口，与后端 schema 一一对应。
- `styles`：维护 Element Plus 主题变量和紧凑布局样式。

页面只能通过 `api` 或 `stores` 访问后端，禁止在 `.vue` 文件中直接拼接请求 URL；公共组件不应包含账号调度等业务规则。

## 6. 数据库和兼容策略

### 6.1 严格不变的数据库约束

Rust 重构必须直接使用当前 AIMux 的 SQLite 数据库。以下内容全部视为不可变的兼容契约：

- 数据库文件格式和现有数据库文件位置规则不变。
- 现有表名、字段名、字段类型、可空性和默认值不变。
- 现有索引、关联关系和数据含义不变。
- 现有数据必须原样保留，不能清空、重建、重命名或批量转换。
- `api_key_encrypted` 等历史字段名必须继续使用，即使字段当前保存的是明文。
- Rust 版本必须能够直接打开当前 Python 版本生成的数据库，并正确读写已有数据。

因此，AIMuxRust 本阶段不执行业务表结构重构，也不修改现有业务数据。数据库层的目标是“替换访问实现，不改变业务数据契约”。Rust 版本以当前数据库中的业务表结构作为自己的 baseline，从此由 Rust 的 SQLx migration 管理后续结构变化。

### 6.2 数据库文件位置

继续使用系统用户数据目录，不把数据库放进安装目录。Windows、macOS 的目录由 Tauri/Rust 的 `app_data_dir` 或 `directories` crate 取得，固定文件名为 `aimux.db`；稳定网关和开发网关始终使用同一个数据库，不再支持自定义 `db_path`。这样升级安装包不会覆盖用户账号和使用记录。

### 6.3 现有数据库读取方式

Rust 版本启动时直接连接当前 SQLite 数据库，并将其视为已完成 baseline。数据库接入必须：

1. 在测试数据库副本上验证旧 Python 版本产生的数据可以完整读取。
2. 对查询结果使用显式 schema/DTO 映射，避免依赖字段顺序。
3. 首次接管只初始化 SQLx 的迁移元数据，不得自动补列、改类型或重建业务表。
4. 发现表结构不匹配时停止启动并给出明确错误，不得静默覆盖用户数据库。

### 6.4 Rust 首个版本的 SQLx baseline

Rust 首个版本不考虑 Python/Alembic 的 migration 执行和版本判断。当前数据库中的 `accounts`、`models`、`usage_records`、`monitor_records` 等业务表结构就是 Rust 的 `0001_baseline` 内容：

- 现有表、字段、索引和业务数据全部保留。
- 首次启动只创建 SQLx 自己的 `_sqlx_migrations` 元数据表，并写入 baseline 已完成记录。
- 旧库中如果存在 `alembic_version`，保留原表和原值，但 Rust 不读取、不更新、不依赖它。
- 后续新增字段、表、索引或约束，只新增 SQLx SQL migration，例如 `0002_add_xxx.sql`。
- 迁移失败时停止启动，不自动清空、重建或覆盖业务数据库。

这样 Rust 首个版本只有一套清晰的数据库版本体系，后续也不再需要 Python 运行时或 Alembic。

### 6.5 密钥处理

当前字段内容已经按明文使用，Rust 版本不应重新引入不可兼容的加密格式。数据库文件仍应受操作系统用户权限保护，日志、错误响应和前端列表不得输出完整 API 密钥。

## 7. 关键业务迁移规则

### 7.1 调度

调度入口统一为 `pick_one(model, account_type)`：

1. 过滤协议类型、启用状态和支持请求模型的账号。
2. 按优先级降序。
3. 同优先级按倍率升序。
4. 再按稳定字段（名称、ID）排序保证结果可预测。
5. 若配置模型映射，调用 `resolve_upstream_model(account, requested_model)` 后再请求上游。

每次失败都重新取号；“重试次数”是单个客户端请求允许的总尝试次数，与账号数量无关。每次尝试独立写入 `usage_records`，成功/失败都更新相应优先级。

### 7.2 流式响应

Rust 必须按字节流转发 SSE，不能等待完整响应后再返回。需要同时完成：

- 首字节/首 Token 计时和总耗时计时。
- 解析最终 usage（可能出现在最后一个 SSE event，也可能没有）。
- 上游中途断开时记录失败尝试，并正确关闭客户端连接。
- 不修改上游事件格式，避免破坏 SDK 的增量解析。

### 7.3 监控

使用 Tokio 后台任务和可取消的 interval。每轮重新读取启用账号，使用 semaphore 控制并发；设置关闭时取消或跳过请求，重新开启后立即执行一轮。监控记录与真实使用记录分开保存，避免统计污染。

### 7.4 管理界面

优先按现有管理 API 逐页迁移：账号、模型、使用记录、数据统计、监控、设置。所有列表必须保留分页、筛选、重置、加载中、空数据、错误和刷新状态。失败状态使用明确的红色，耗时超过阈值使用黄色，避免只依赖文字颜色。

## 8. 迁移方式和阶段计划

### 阶段一：工程骨架

- 创建 Vite + Vue 3 + TypeScript 项目和 Tauri 2 项目。
- 配置 Element Plus、Pinia、ESLint/Prettier、Rust `cargo fmt`/`clippy`。
- 建立 Rust 配置、日志、应用数据目录和 SQLite 连接。

### 阶段二：数据库和管理 API

- 完成现有 SQLite 表结构检查、SQLx baseline 接管和旧库读取验证，不修改业务表和已有数据。
- 先实现账号、模型、设置 CRUD，再实现使用记录、统计和监控查询。
- 为 DTO、分页参数、错误响应建立稳定契约。

### 阶段三：网关核心

- 实现模型列举、账号选择、倍率排序、模型映射和总重试。
- 实现 OpenAI/Anthropic 非流式端点。
- 加入每次尝试记录和 Token/缓存 Token 解析。

### 阶段四：流式、监控和桌面能力

- 实现 SSE 转发和耗时统计。
- 加入监控后台任务、优先级规则、代理和超时设置。
- 实现打开数据目录、检查更新、窗口和退出等 Tauri command。

### 阶段五：前端页面

- 按页面逐个替换旧 PySide6 界面，复用表格、分页、状态标签和表单组件。
- 先完成账号/模型/设置，再完成使用记录/统计/监控。
- 与旧版本截图和 API 响应进行回归对比。

### 阶段六：打包和切换

- 配置 Windows x64/arm64、macOS x64/arm64 构建矩阵。
- 在真实旧数据库副本上验证升级、回滚备份和全功能操作。
- 新旧版本并行试用，确认网关协议、数据和性能无回归后再发布。

## 9. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Rust 与 Python 的 JSON/错误语义不一致 | 客户端兼容性回归 | 固化 API 契约和响应样例，增加协议回归测试 |
| SSE usage 不在首个响应中 | Token 和缓存统计缺失 | 解析完整 event 流，流结束时统一结算记录 |
| SQLite 并发读写 | 锁等待或数据丢失 | 单连接池、短事务、WAL、写入重试和专项测试 |
| Tauri command 与 HTTP API 逻辑重复 | 行为分叉 | 管理页面统一调用 HTTP API，command 只做桌面能力 |
| 跨平台代理/TLS/证书差异 | 上游请求失败 | reqwest 平台测试，错误日志区分 DNS、连接、TLS 和 HTTP 状态 |
| 安装升级覆盖数据 | 用户数据丢失 | 数据目录与安装目录分离，升级前自动备份 |
| 首次启动或打包体积 | 用户体验变差 | Vite 资源拆分、Rust release 优化、保留增量构建缓存 |

## 10. 测试策略

- Rust 单元测试：调度排序、倍率、模型映射、重试次数、Token 解析和优先级边界。
- Rust 集成测试：现有 SQLite 结构/数据兼容性、SQLx baseline 和后续 migration、管理 API、OpenAI/Anthropic 非流式和 SSE 流式。
- 前端测试：Pinia store、分页筛选、表单校验和错误/空数据状态。
- Tauri 冒烟测试：启动、窗口、打开数据目录、关闭、升级后数据保留。
- 跨平台验证：Windows x64/arm64、macOS Intel/Apple Silicon 的安装和网关访问。

日常改动只运行受影响范围的测试；调度、数据库、HTTP 生命周期或发布流程等共享基础设施变更，再运行完整测试和跨平台构建验证。

## 11. 结论

这套技术栈适合 AIMux，但工作量属于中大型重构。最大成本不在 Vue 页面，而在保持网关协议、流式响应、旧 SQLite 数据和调度细节完全兼容。建议将 AIMuxRust 作为独立目录逐步实现，先完成数据库/API 和协议回归，再替换界面，避免一次性切换导致无法定位问题。
